### 이후 Task에 주는 정보

- 스왑이 0B이므로 OpenSearch가 요구하는 "스왑 끄기"는 이미 충족된 상태다(Task 6).
- Docker가 없으므로 결정(Docker 미사용)과 맞는다.
- **보안 관찰과 조치(해결됨):** 처음에는 비밀번호 로그인(`passwordauthentication yes`)과 root 로그인(`permitrootlogin yes`)이 모두 켜져 있고 22번 포트가 인터넷에 열려 있었다. 원인과 조치는 아래와 같다(명령마다 사용자 승인, 2026-11-18).
  - 원인: sshd는 `sshd_config.d/*.conf`를 번호 순으로 읽고 **먼저 나온 값이 이긴다**. `50-cloud-init.conf`가 `PasswordAuthentication yes`, 뒤의 `60-cloudimg-settings.conf`가 `no`라서 50번이 이겼다. `PermitRootLogin yes`는 본 설정 `sshd_config` 42번 줄에 있었다.
  - 조치: cloud-init이 관리하는 파일은 건드리지 않고 `/etc/ssh/sshd_config.d/00-hardening.conf`를 추가했다(내용: `PasswordAuthentication no`, `PermitRootLogin prohibit-password`). 이름이 00이라 먼저 읽힌다.
  - 적용 전 확인: `sshd -t` 문법 정상(exit 0), `sshd -T`가 `passwordauthentication no`·`permitrootlogin without-password`·`kbdinteractiveauthentication no`·`pubkeyauthentication yes`를 보여 줌. root에 등록된 키는 하나이고 지문이 이 PC 에이전트의 키와 같음.
  - 적용: `systemctl reload ssh` (열린 접속은 끊기지 않음).
  - 적용 후 확인: 키로 새 연결 성공(`echo key-login-ok`), `ssh.service`·`ssh.socket` 모두 active. 클라이언트 쪽 `ssh -v`의 `Authentications that can continue`가 적용 전 `publickey,password` → 적용 후 `publickey`로 바뀜.
  - **되돌리는 방법:** 서버에서 `rm /etc/ssh/sshd_config.d/00-hardening.conf && systemctl reload ssh`. 접속이 아예 안 되면 Contabo 고객 패널의 VNC 콘솔로 같은 명령을 실행한다(콘솔 접근은 확인하지 못함).
  - 이 PC 쪽 설정: 별칭 `contabo`(`~/.ssh/config`), 키는 `ssh-agent`가 보관(서비스 자동 시작). `~/.ssh` 폴더 권한은 `GeneralUser`를 뺀 세 곳으로 좁힘.

### 읽는 법과 한계

- **Cohere:** 10번 성공한 뒤 11번째에서 429가 났고, 전체가 6.84초 안이었다. 기억해 둔 "시험 키 Rerank 분당 10회"와 맞아떨어진다. 모델 이름 `rerank-v5.0-pro`는 Cohere 공식 문서(`docs.cohere.com/docs/rerank-overview`)의 모델 목록에 그대로 있었다(Task 8의 이름 추측이 맞음). 429에 대기 시간 정보는 오지 않았다(`retry_after_s` 없음). 이번 측정으로 월 호출 한도 1,000회 중 약 11~12회를 썼다(429 호출이 세어지는지는 모른다).
- **Gemini 5개 모델과 임베딩:** 12번 안에서는 한 번도 429가 나지 않았다. 이것은 "한도가 12회보다 크다"까지만 말해 준다. **분당·일일 한도의 실제 숫자는 이번 측정으로 알 수 없다**(상한을 12로 둔 설계였고 한도에 닿지 않음). 그래서 Task 7의 색인 예산(해석 전량 임베딩이 하루에 들어가는가)은 아직 계산할 수 없다. 이 값은 Task 7에서 대량 임베딩을 하며 429가 나는 지점을 직접 보고 정하거나, 한도를 더 크게 잡은 측정을 따로 하면 알 수 있다.
- **키가 무료 요금제의 것인지는 이번 측정이 보여 주지 않는다.** 호출이 성공했다는 사실만으로는 무료 프로젝트인지 결제가 연결된 프로젝트인지 구분되지 않는다. 월 청구액 0원 조건을 지키려면 사용자가 Google AI Studio에서 이 키의 프로젝트가 무료(Free tier)로 표시되는지 확인해야 한다.
- 호출 한 건의 입력은 짧은 시험 문장이다. 실제 조문 길이(수천 자)에서는 분당 토큰 한도가 먼저 닿을 수 있다 — 이것은 가능성일 뿐 측정한 것이 아니다.
- Gemini의 429 응답에서 `retryDelay`를 읽는 코드는 Google의 RetryInfo 형식을 가정하고 만들었다. 이번에 Gemini 429가 한 번도 나지 않아서 **실제 응답으로는 아직 검증되지 않았다.**

### 8-5. 읽는 법과 한계

- **두 문장의 차이가 크다.** MRR(RRF 순서)이 조문 어휘형 0.96, 일상어형 0.50이다. 조문 단어를 그대로 쓴 질문은 정답이 거의 1등으로 나오고, 일상어 질문은 정답이 1등으로 나오는 경우가 크게 줄었다는 뜻이다(MRR은 순위의 평균이 아니라 1/순위의 평균이라서 0.50을 "평균 몇 등"으로 읽으면 안 된다). 스펙 개정 1이 걱정한 "조문에서 질문을 만들면 점수가 부풀려진다"가 이 표본에서 실제로 보인다. 일상어형이 실제 사용에 더 가깝지만, 그 질문도 조문을 읽은 같은 작성자(Claude)가 썼고 사람 검수가 없어서 완전히 독립적이지 않다.
- **리랭크가 순위를 크게 끌어올렸다.** 일상어형 MRR이 0.50(RRF)에서 0.88(리랭크 뒤)로 올랐다. 다만 리랭크 MRR은 상위 5개 안에서만 세고 RRF MRR은 상위 20개 안에서 센다.
- **깊이는 결론을 낼 수 없다.** 일상어형 Recall@20이 깊이 100·150·200에서 0.94·0.86·0.90으로 깊이에 따라 단조롭게 변하지 않는다. 조문 어휘형(0.99)과 MRR(0.50)은 깊이와 무관했다. 표본이 34건이고 한 번씩만 돌렸다. 러너의 선택 규칙(평균 Recall → MRR → 작은 깊이)은 100을 골랐지만 "100이 낫다"고 말할 근거는 아니다. 게다가 `pagination_depth`가 RRF에서 하위 쿼리별 후보 수를 정한다는 것은 아직 증명되지 않았다(Task 6 기록). 측정 당시 `Settings.search_depth`는 150이었고, 이 표를 본 뒤 사용자가 100으로 바꾸기로 했다(2026-11-18, 우연일 수 있어 Task 17에서 다시 확인).
- **임계값은 후보일 뿐이다.** 정답 없는 질문이 6건, 정답이 빠진 질문이 1건뿐이다. 일상어형 후보 0.15는 답할 수 있는 질문의 91%를 통과시키는데, 이는 정답이 상위 5에 들었는데도 1위 점수가 0.15 미만인 질문이 33건 중 약 3건 있다는 뜻이다(비율에서 거꾸로 센 값). 어느 질문인지는 이 표에서는 알 수 없다. 측정 당시 `rerank_min_score`는 임시값 0.0이라 리랭크 경로의 충분성 판단이 항상 "충분"이었다. **이 측정을 본 뒤 사용자가 일상어형 후보 0.15로 정했다(2026-11-18).** 서비스 전체에서의 효과는 아직 재지 않았다(Task 17).
- **Cohere 호출 수.** 위 80회는 이 PC의 평가용 DB(`data/eval.db`)가 센 값이다. Cohere의 실제 월 1,000회는 서버 앱의 호출과 합산되며 서버 카운터는 이 호출을 모른다. 이번 달 이 키의 총 사용량은 확인하지 못했다.

**한도 사용(이 1회 실행).** LLM 118회, 임베딩 34회, Cohere 리랭크 34회(Cohere 월 한도 1,000회의 3.4%, 앱 상한 950회의 3.6%). 이 PC의 평가용 DB가 센 이번 달 리랭크 호출 수는 144 → 178. 실제 Cohere 키의 월 합계는 서버 앱 호출과 합쳐지므로 이 PC에서는 알 수 없다.

## 12. Langfuse 질문당 units 결과와 검증기 대조 확인 (Task 16 Step 5 마무리, Task 17 Step 6·8, 2026-11-19)

### 12-1. Langfuse 질문당 units (Task 16 Step 5의 결과, 9절의 실행에 대한 숫자)

**어떻게 셌나.** 사용자가 결제 화면의 막대 숫자를 읽는 대신, 이 프로젝트의 Langfuse 키로 읽기 전용 API를 불러 9절 실행 구간(UTC 2026-11-18 12:25~12:40)의 개수를 직접 셌다. 개수와 종류만 출력했고 기록 내용(질문 글)은 읽지 않았다. 결제 화면의 막대는 읽지 않았다.
- 예전 읽기 주소(`GET /api/public/traces`, `/observations`, `/scores`)는 **HTTP 410**이었다: 응답이 "Langfuse v3 API는 2026-11-16~18 일시 차단을 거쳐 2026-11-19에 제거된다"며 `GET /api/public/v2/observations`(점수는 `GET /api/public/v3/scores`)를 알려 줬다. 그 주소로 셌다.
- 하루 전체(UTC 11-18)로 넓혀도 개수가 같아서 다른 기록이 섞이지 않았다(시작 시각 12:30:15~12:32:11).

**결과.**

| 항목 | 개수 |
|---|---|
| trace(질문) | 10 |
| observation | 447 (CHAIN 359, EVENT 61, GENERATION 27) |
| score | 0 (피드백 버튼을 쓴 적이 없다) |
| units (= trace + observation + score, Langfuse 문서 기준) | **457 → 질문당 평균 45.7** |

질문 종류별(trace별 observation 수): 거절 2건 16개(GENERATION 1), 답변 7건 각 50개(GENERATION 3), 다시 쓴 1건 65개(GENERATION 4). 즉 **답변 한 건 51 units, 거절 한 건 17 units, 다시 쓴 답변 66 units**다(각각 trace 1개를 더한 값).

**월 50,000 units에 비춰 본 용량(추정).** 평균(45.7)으로 약 1,094건, 답변만 오는 경우(51)로 약 980건, 가장 큰 trace(66)로 약 757건이다. 평가 실행(`eval/run_eval.py`)은 Langfuse에 보내지 않으므로(코드가 추적을 끈다) units를 쓰지 않는다. 계정 `test`는 IP당 5회로 제한되어 있어 이 용량으로 시연에는 충분해 보이지만 실제 사용량은 모른다.

**전에 쟀던 값과의 차이.** 7절의 가짜 LLM 측정은 질문당 span 20개였다. 진짜 모델로는 답변 한 건이 observation 50개라서 **2.5배**다. 7절의 값은 용량 계산에 쓰지 않는다.

**모르는 것.** (1) 결제 화면이 센 units가 위 합(457)과 같은지는 확인하지 않았다(문서의 정의를 따른 계산이다). (2) 한도를 넘으면 Langfuse가 어떻게 동작하는지, 그때 앱이 영향받지 않는지(`app/graph/build.py`는 기록 오류를 삼키지만 SDK의 비동기 전송 실패는 시험하지 않았다). (3) **점수(피드백 👍/👎) 쓰기**: SDK 5.2.0의 `create_score`는 `POST /api/public/scores`로 보낸다(`.venv/.../langfuse/_client/resource_manager.py:488`). 폐지된 것은 GET v3 읽기 주소로 보이지만 POST가 지금도 되는지는 점수를 실제로 보내 봐야 안다 — **Task 18 배포 때 한 번 보내 확인한다.**

### 12-2. 검증기 대조 확인 (사람이 아님)

**배경.** 사용자가 검증기 라벨을 "20~25문장 표시"로 정했다가(2026-11-19) "네가 판단해줘"라고 맡겼다. 규칙상 Claude의 판정은 **사람 라벨이 아니다**: 가져오기 코드도 `claude` 검수자를 거부하고(`eval/labels.py`), 평가셋도 Claude가 초안을 썼다. 그래서 사람 라벨 시트(`data/validator_sheet.csv`)는 비워 두었고, **사람이 확인한 건수는 0**, 리포트의 "검증기 정확도"는 "측정 불가"로 남는다.

**한 일.** Claude가 시트의 문장 25개를 인용한 조문 본문과 직접 대조했다. 일반 질문 22개(시트의 짝수 번째 줄)와 사건 판단 질문 3개(v01, v02, v04). 판단 기준은 "문장이 인용 조문에 적힌 내용과 모순되지 않고 조문이 그 내용을 뒷받침하는가"다.

**결과.** 25문장 모두 인용 조문이 뒷받침한다고 판단했다. 검증기(Gemini)도 나간 문장은 모두 "일치"였으므로(나간 답변은 전 문장이 통과한 것이다) 두 판정이 25/25로 같다. 다만:
- 두 문장은 "뒷받침되지만 단순화했다"고 보았다: a12#2(해고 예고 수당, 예외 3가지 생략), a21#3(휴업수당, 통상임금으로 지급하는 경우의 조건 생략). 둘 다 틀린 내용은 아니다.
- **이 확인의 한계**: ① 사람이 아니다. ② 같은 LLM 계열이 같은 문장을 보는 검사라 독립성이 약하다. ③ 최종 답변은 전 문장이 검증을 통과한 것이라, 이 표본은 "검증기가 **틀린 문장을 통과시켰는가**"만 볼 수 있고 "맞는 문장을 잘못 떨어뜨렸는가"는 볼 수 없다(떨어진 문장은 다시 쓰이면서 사라진다). ④ 25개는 같은 평가 질문에서 나왔다. ⑤ 문장이 질문에 **알맞은 답인지**(관련성)는 보지 않았다 — 예를 들어 a13은 "이유 없이 해고할 수 있는가"에 해고 예고 규정을 인용했다. 검증기도 이것을 보지 않는다.
- 즉 "검증기 정확도 25/25"라고 쓰면 안 되고, "Claude 대조에서 불일치 0건(표본 25문장, 사람 확인 아님)"까지만 말할 수 있다.

### 12-3. Task 17 관문(Step 8) 판단

사용자가 판단을 맡겼다(2026-11-19). **판단: 통과.** 합격선 세 개(인용 ≥ 0.80, 오거절 ≤ 15%, 거절 ≥ 0.80)를 전체 40건에서 모두 넘었고(11절), 부족한 지표가 없어서 검색·프롬프트·임계값·모델을 고치지 않는다. 남은 위험은 점수가 아니라 **시험되지 않은 경로**다: 근로 질문인데 수집 범위 안에 답이 없는 경우(검색은 되지만 근거가 부족해 "모른다"고 답해야 하는 경우)가 평가셋에 없다. 이 경우 서비스가 관련 없는 조문으로 답을 만들고 검증기가 그 문장은 조문과 맞다며 통과시킬 수 있다(추정 — 검증기는 문장과 조문의 일치만 보고 질문과의 관련성은 보지 않는다). 어려운 거절 질문 몇 건을 평가셋에 더해 같은 러너로 재는 일을 Task 18 최종 측정 전에 하기를 권한다(서버 연결 승인이 필요하다).
