### 이후 Task에 주는 정보

- 스왑이 0B이므로 OpenSearch가 요구하는 "스왑 끄기"는 이미 충족된 상태다(Task 6).
- Docker가 없으므로 결정(Docker 미사용)과 맞는다.
- **보안 관찰과 조치(해결됨):** 처음에는 비밀번호 로그인(`passwordauthentication yes`)과 root 로그인(`permitrootlogin yes`)이 모두 켜져 있고 22번 포트가 인터넷에 열려 있었다. 원인과 조치는 아래와 같다(명령마다 사용자 승인, 2026-11-18).
  - 원인: sshd는 `sshd_config.d/*.conf`를 번호 순으로 읽고 **먼저 나온 값이 이긴다**. `50-cloud-init.conf`가 `PasswordAuthentication yes`, 뒤의 `60-cloudimg-settings.conf`가 `no`라서 50번이 이겼다. `PermitRootLogin yes`는 본 설정 `sshd_config` 42번 줄에 있었다.
  - 조치: cloud-init이 관리하는 파일은 건드리지 않고 `/etc/ssh/sshd_config.d/00-hardening.conf`를 추가했다(내용: `PasswordAuthentication no`, `PermitRootLogin prohibit-password`). 이름이 00이라 먼저 읽힌다.
  - 적용 전 확인: `sshd -t` 문법 정상(exit 0), `sshd -T`가 `passwordauthentication no`·`permitrootlogin without-password`·`kbdinteractiveauthentication no`·`pubkeyauthentication yes`를 보여 줌. root에 등록된 키는 하나이고 지문이 이 PC 에이전트의 키와 같음.
  - 적용: `systemctl reload ssh` (열린 접속은 끊기지 않음).
  - 적용 후 확인: 키로 새 연결 성공(`echo key-login-ok`), `ssh.service`·`ssh.socket` 모두 active. 클라이언트 쪽 `ssh -v`의 `Authentications that can continue`가 적용 전 `publickey,password` → 적용 후 `publickey`로 바뀜.
  - **되돌리는 방법:** 서버에서 `rm /etc/ssh/sshd_config.d/00-hardening.conf && systemctl reload ssh`. 접속이 아예 안 되면 Contabo 고객 패널의 VNC 콘솔로 같은 명령을 실행한다(콘솔 접근은 확인하지 못함).
  - 이 PC 쪽 설정: 별칭 `contabo`(`~/.ssh/config`), 키는 `ssh-agent`가 보관(서비스 자동 시작). `~/.ssh` 폴더 권한은 `GeneralUser`를 뺀 세 곳으로 좁힘.

### 읽는 법과 한계

- **Cohere:** 10번 성공한 뒤 11번째에서 429가 났고, 전체가 6.84초 안이었다. 기억해 둔 "시험 키 Rerank 분당 10회"와 맞아떨어진다. 모델 이름 `rerank-v5.0-pro`는 Cohere 공식 문서(`docs.cohere.com/docs/rerank-overview`)의 모델 목록에 그대로 있었다(Task 8의 이름 추측이 맞음). 429에 대기 시간 정보는 오지 않았다(`retry_after_s` 없음). 이번 측정으로 월 호출 한도 1,000회 중 약 11~12회를 썼다(429 호출이 세어지는지는 모른다).
- **Gemini 5개 모델과 임베딩:** 12번 안에서는 한 번도 429가 나지 않았다. 이것은 "한도가 12회보다 크다"까지만 말해 준다. **분당·일일 한도의 실제 숫자는 이번 측정으로 알 수 없다**(상한을 12로 둔 설계였고 한도에 닿지 않음). 그래서 Task 7의 색인 예산(해석 전량 임베딩이 하루에 들어가는가)은 아직 계산할 수 없다. 이 값은 Task 7에서 대량 임베딩을 하며 429가 나는 지점을 직접 보고 정하거나, 한도를 더 크게 잡은 측정을 따로 하면 알 수 있다.
- **키가 무료 요금제의 것인지는 이번 측정이 보여 주지 않는다.** 호출이 성공했다는 사실만으로는 무료 프로젝트인지 결제가 연결된 프로젝트인지 구분되지 않는다. 월 청구액 0원 조건을 지키려면 사용자가 Google AI Studio에서 이 키의 프로젝트가 무료(Free tier)로 표시되는지 확인해야 한다.
- 호출 한 건의 입력은 짧은 시험 문장이다. 실제 조문 길이(수천 자)에서는 분당 토큰 한도가 먼저 닿을 수 있다 — 이것은 가능성일 뿐 측정한 것이 아니다.
- Gemini의 429 응답에서 `retryDelay`를 읽는 코드는 Google의 RetryInfo 형식을 가정하고 만들었다. 이번에 Gemini 429가 한 번도 나지 않아서 **실제 응답으로는 아직 검증되지 않았다.**

  상한에 대해서는 아무것도 말해 주지 않는다. 2절의 "실제 RPM/RPD를 찾지 못함"은 그대로다.
- **비용:** 임베딩 단가를 확인하지 못했다. 사용자는 AI Studio의 사용량 화면에서 이번 실행(요청 15번, 약 29만 글자)이 크레딧에서 얼마를 썼는지 한 번 확인하면
  좋다. 자동결제가 꺼져 있다는 것은 사용자 진술이다.
- **검색 품질은 이 측정으로 알 수 없다.** 배선 확인용으로 질문 2개를 던져 봤을 뿐이다(평가셋 없음).
  - "근로기준법 제56조" → 1위 근로기준법 제56조, 2위 근로기준법 시행령 제56조. 조문번호 정확 일치와 법령명 가산이 의도대로 동작.
  - "주휴수당 받으려면 일주일에 몇 시간 일해야 해요?" → 상위 5개(근로기준법 제69조, 최저임금법 시행령 제5조, 근로기준법 제50조·제46조,
    근로기준법 시행령 제6조)에 주휴수당의 근거인 근로기준법 제55조(휴일)가 **없었다.** 질문 1개이므로 결론이 아니다.
    법령 본문은 "주휴수당"이 아니라 "유급휴일"이라고 쓰므로 어휘 차이일 가능성이 있다(추정). 질문 재작성(Task 10)과 리랭크(Task 8)가 메우는
    역할이며, 얼마나 메우는지는 평가셋이 있어야(Task 9) 잴 수 있다.
- 다시 실행하면 처음부터 다시 임베딩한다(이미 들어간 청크를 건너뛰지 않는다). 같은 `chunk_id`는 덮어쓰므로 중복되지는 않는다.

## 6. API 스모크: 진짜 부품으로 질문 2개 (Task 14, 2026-11-18)

목적: Task 10~14의 코드(그래프·API)가 **진짜** Gemini·Cohere·OpenSearch와 한 번이라도 맞물려 도는지 확인한다. 평가가 아니다(질문 2개).
방법: 임시 스크립트(저장소 밖)가 앱(`create_app`)을 한 프로세스 안에서 띄우고, 임시 로그인으로 `/api/chat`에 질문 2개를 보냈다(같은 대화).
OpenSearch는 SSH 터널(읽기 전용)로 서버의 `labor-rag-v1`을 썼고, SQLite(앱 DB·체크포인트)는 임시 폴더에 만들었다. 채팅 모델은 임시값
`gemini-3.5-flash-lite`, 리랭크는 `rerank-v5.0-pro`, 임베딩은 `gemini-embedding-2`(768)다. 키 값은 출력하지 않았다.

| 항목 | 질문 1 "주 15시간 일하면 주휴수당 받아?" | 질문 2 "그럼 알바는요?" (같은 대화) |
|---|---|---|
| HTTP·소요 | 200 · 7.6초 | 200 · 5.8초 |
| LLM 호출 수 (그래프 상태 `llm_calls`) | 3 (분석·생성·검증) | 3 |
| 분류·분기 | counsel · 리랭커 사용 · 재검색 0 · 재생성 0 | 같음 |
| 검색 단계 요약(앞 3개) | 근로기준법 시행령 제30조, 근로기준법 제56조, 제55조 … | 기간제 및 단시간근로자 보호 등에 관한 법률 제17조, 근로기준법 제55조, 근로기준법 시행령 제30조 … |
| 답변 | 2문장(근거 1 + 설명 1), 인용 `근로기준법 제18조` | 4문장(근거 2 + 설명 2), 인용 `근로기준법 제55조`, `근로기준법 시행령 제30조` |
| Cohere 리랭크 시도 | 합계 2회(질문당 1회) · 오류·429 없음 · 로그 경고 없음 | |

**원문으로 확인한 것** (`data/manual`을 `parse_law_file`로 읽어 해당 청크 본문과 대조):
- 질문 1의 근거 문장("4주 동안을 평균하여 1주 동안의 소정근로시간이 15시간 미만인 근로자에 대하여는 … 제55조가 적용되지 않습니다")은
  근로기준법 제18조 ③("… 15시간 미만인 근로자에 대하여는 제55조와 제60조를 적용하지 아니한다")와 일치하고, 인용한 출처도 그 조문이다.
- 질문 2의 근거 문장 두 개는 근로기준법 제55조 ①, 근로기준법 시행령 제30조 ①과 일치한다.

**이 측정으로 알 수 있는 것**
- 실제 Gemini에서 구조화 출력 스키마 3개(`Analysis`, `GeneratedAnswer`, `Verification`)가 오류 없이 왕복했다(이전에는 가짜 LLM으로만 시험). 이 경로에서
  호출되지 않은 `Sufficiency`·`Refined`(리랭커를 쓰면 LLM 판정이 없고, 재검색이 없었음)는 아직 실제 호출을 못 봤다.
- 정상 경로의 LLM 호출 수가 두 질문 모두 3으로 측정됐다(설계서가 말한 정상 경로 3~4회 안이다. 2건뿐이라 분포는 모른다).
- 같은 `thread_id`로 두 번째 질문이 진짜 SQLite 체크포인트 위에서 이어졌다(오류 없음). 두 번째 질문의 검색 결과가 단시간근로자 법령으로 바뀐 것은
  앞 대화를 반영한 질문 재작성 덕분일 것이다(추정 — 재작성된 검색어를 출력하지 않아 직접 확인하지 못했다).
- Task 7의 첫 스모크("주휴수당" 질문이 제55조를 상위 5개에 못 넣음)와 비교하면, 이번에는 질문 재작성+리랭크를 거친 검색 요약에 제55조가 들어 있다(질문이
  같은 문장이 아니고 n=1~2라서 개선이라고 결론 내리지 않는다. 측정은 Task 9의 평가셋이 해야 한다).

**알 수 없는 것 (미확인, 그대로 남음)**
- 응답 시간 분포: 한 번씩 잰 값(7.6초, 5.8초)뿐이다. 서버에서 돌린 값이 아니라 이 PC에서 SSH 터널을 거친 값이라 운영 지연과 다르다.
- Gemini 무료 한도: 429가 한 번도 나오지 않아 실제 429의 모양(retryDelay)과 한도 숫자는 여전히 모른다(키가 순수 무료 프로젝트가 아님, 3절·5절 참고).
- 답변 품질: 질문 1은 정확히 "15시간"을 물었는데 답은 "15시간 미만"의 규칙을 보여 주고 사실관계가 부족하다고 밝혔다. 이 동작이 설계(사건 판단 없이 규칙 설명)에
  맞는지, 평균적으로 좋은지는 Task 17의 평가가 판단한다.
- 충분성 판단: 리랭크 임계값이 임시값 0.0이라 두 질문 모두 "충분함"이다(Task 9의 측정이 정한다).
- 근로기준법 제55조 청크의 본문에는 `[시행일] …` 경과 규정 줄이 섞여 있다(Task 4의 알려진 한계). 이번 답변에는 영향이 없었지만 인용 카드의 원문에는 보인다.
- 출처 링크 `https://www.law.go.kr/법령/근로기준법%20시행령/제30조`(공백이 `%20`)가 실제로 열리는지는 확인하지 않았다.
